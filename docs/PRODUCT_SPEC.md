# MASA Salon Intelligence 製品仕様書

## 文書の位置づけ

この文書は、MASA Salon Intelligenceの全体構想と製品仕様の正本とする。現行コードの実装事実は `CURRENT_IMPLEMENTATION.md`、実装順序は `ROADMAP.md`、重要な判断は `DECISIONS.md` を参照する。

## 仕様状態

- `CONFIRMED`: ユーザーにより確定した仕様
- `DRAFT`: 将来構想、方向性、検討中の案

- `OUT_OF_SCOPE`: 対象外と決定した事項

## 1. システムの基本目的

**状態: `CONFIRMED`**

MASA Salon Intelligenceは、美容室の日々の実績データ、売上、客数、稼働率、価格、Hot Pepper Beautyの集客データ、失客・リピート、経費・利益・借入返済などを統合し、経営判断を支援するシステムを目指す。

単なる売上管理アプリやKPI確認システムではなく、最終的にはAIがデータを分析し、価格改定、集客、メニュー、経営改善などについて提案する「AI経営判断支援システム」を目指す。「AI社長室」は、その役割を担う機能として位置づける。

### AIとユーザーの権限

**状態: `CONFIRMED`**

- AIは分析と提案を行う。
- 重要な経営判断をAIが勝手に実行しない。
- 最終判断はユーザーが行う。
- 重要な変更はユーザーの確認後に実行する。

### 1.1 経営判断支援の基本サイクル

**状態: `CONFIRMED`**

MASA Salon Intelligenceの基本サイクルは、次のとおりとする。

`データ → 原因分析 → 仮説 → 具体的な行動提案 → 実行 → 効果検証 → 学習 → 次の提案`

単発の数値確認や、数字を見れば誰でも言える抽象的な助言で終わらず、実行後の結果を次の経営判断へつなげる。

### 1.2 最上位の経営目標

**状態: `CONFIRMED`**

売上最大化だけを目的とせず、次の5つを総合して経営判断する。

- giggleの利益を増やす。
- スタッフの給与を上げられる状態を作る。
- オーナーが家計に入れられる収入を増やす。
- オーナーの労働時間・負担をむやみに増やさない。
- 顧客満足を犠牲にしない。

売上増加が見込める施策であっても、利益、時間、スタッフ負担、顧客満足などを総合して不適切であれば採用しない。

### 1.3 何もしない判断

**状態: `CONFIRMED`**

「今は何もしない」「今月は変更しない」ことも、正式な経営判断の選択肢とする。

## 3. 日々の来店実績

**状態: `CONFIRMED`**

- 1人の顧客につき担当スタッフは1人とする。
- 来店時間は30分刻みを基本とする。
- メニュー選択時に標準価格と標準所要時間を自動入力する。
- 実際の価格と所要時間は来店ごとに変更できる。
- 最終確定した所要時間を分析に使用する。
- 終了時刻は `来店時間 + 確定所要時間` で自動計算する。
- 売上、時間、時間単価、稼働率を担当スタッフに紐づける。
- 店販売上は日単位で入力する。

**状態: `CONFIRMED`**

### フェーズ1の担当スタッフ分析基礎（F1-001）

**状態: `CONFIRMED`（2026-09-24採用）**

完了定義は「各実績に担当スタッフが正しく紐づいて保存され、将来スタッフ別分析に利用できるデータ構造になっていること」とする。スタッフ別売上画面、客単価、時間単価、稼働率その他のスタッフ別分析画面の新規実装はフェーズ1の必須条件に含めず、将来フェーズで扱う。旧データの欠落履歴は3.3に従い推測補完しない。

### 3.1.1 実績修正時の更新ルール

**状態: `CONFIRMED`**

- 実売上だけを変更した場合、`standardPriceAtVisit` は変更しない。
- 所要時間だけを変更した場合、`standardPriceAtVisit` は変更しない。
- 担当者を変更した場合、`staffId` と `staffNameAtVisit` を新しい担当者の値に更新する。
- メニューを変更した場合、`menuId`、`menuName`、`standardPriceAtVisit` を新しいメニューの値に更新する。

### 3.2 営業日の状態

**状態: `CONFIRMED`**

日別データに `businessStatus` を追加し、次の値で状態を区別する。

- `open`: 営業
- `closed`: 休業
- `unset`: 未設定

保存・判定ルールは次のとおり。

- 何も保存していない日は `unset` とする。
- 通常どおり「営業設定を保存」した日は、別の営業選択操作を求めず `open` として保存する。
- ユーザーが明示的に休業を選択して保存した日は `closed` とする。
- `closed` の日には原則として来店実績を登録できない。
- 休業日に臨時の来店実績を登録する場合は、先にその日の営業設定を通常保存し、`open` に変更してから登録する。

### 3.3 保存形式と後方互換性

**方針の状態: `CONFIRMED`**

- `localStorage` キーは `masa_salon_intelligence_prod_v1` を維持する。
- 旧データに新フィールドが存在しなくても読み込めるようにする。
- 旧実績に `standardPriceAtVisit` がない場合、現在のメニューマスター価格または実売上から推測して保存しない。
- 旧実績に `staffNameAtVisit` がない場合、確実に復元できない名前を推測して保存しない。
- 旧日別データに `businessStatus` がない場合、実績、売上、勤務設定から営業または休業を推測せず、`unset` として扱う。
- 価格改定履歴管理と適用開始日の本格管理はフェーズ2で実装する。
- フェーズ1では新規・修正実績の `standardPriceAtVisit` を保持し、価格改定履歴管理そのものは実装しない。

### 3.4 データバージョン2の適用条件

**状態: `CONFIRMED`**

フェーズ1では `version: 2` を保存形式として採用した。現在の複数メニュー形式は3.6のversion 3を適用する。以下はフェーズ1導入時に実施した条件の記録である。

1. 現在の保存データのJSONバックアップを確保する。
2. 現在稼働環境と分離したテスト環境で検証する。
3. `version: 1` の保存データを読み込めることを確認する。
4. 既存のJSONバックアップを復元できることを確認する。
5. 新旧アプリ間の往復で既存データと新フィールドが欠損しないか確認する。

これらの互換性テストに合格するまで、現在稼働版に `version: 2` を適用しない。

2026-09-24採用の保証範囲: 新→旧→新の単純な保存・読込みで既存項目と新フィールドを保持する。履歴保存仕様を持たない旧版で担当者・メニューを編集した場合まで、新仕様の履歴整合性を保証しない。履歴値を推測補完せず、この旧版編集の制約はフェーズ1の完了を妨げる不具合とは扱わない。現行版には3.1.1を引き続き適用する。

未運用の場合も公開アプリの現在の設定・データをJSONとして確保することでバックアップ要件を満たす。実績件数は条件とせず、取得元・取得時点・原本の識別情報と、コピーによる隔離復元結果を記録する。

- 総売上は `技術売上 + 店販売上` とし、別指標として表示する。

### 3.6 複数メニュー来店とデータversion 3

**状態: `CONFIRMED`（2026-10-01、ユーザーの正式実装指示）**

- 1実績（entry）は1来店・1人・1担当のまま。来店共通の `id`、`staffId`、`staffNameAtVisit`、`arrival`、`price`、`minutes` を保持する。
- 新規実績は単一メニューでも `menuItems` 配列に明細を保存する。明細は `id`、`menuId`、`menuName`、`standardPriceAtVisit`、`price`、`standardMinutesAtVisit`、`categoryAtVisit` を持つ。
- 明細の実売上は0以上の有限数値。来店priceは明細price合計と一致させる。値引きは明細ごとに入力し、自動按分しない。不整合のバックアップは補正せず拒否する。
- 新規入力の滞在時間初期値は選択メニューの標準時間合計。手動編集後はその値を維持する。既存実績編集では保存済みの最終minutesを維持し、必要なら手動修正する。終了時刻・時間単価・稼働率には最終minutesのみを使用し、実時間を明細へ按分しない。
- マスターの名称・価格・時間・カテゴリー変更や削除は過去明細へ反映しない。明示的にメニューIDを変更した明細だけ、選択先の履歴値へ更新する。担当者履歴は既存ルールを維持する。
- category未設定の新規メニュー選択時は空文字を来店時の未分類として保存する。旧実績でcategoryAtVisitが欠落している場合は不明とし、現在マスターから補完しない。0と欠落を区別する。
- 旧単一メニュー実績は表示・集計時だけ単一明細相当として読み取る。通常編集で構造を変えず、ユーザーが複数明細にして保存した場合だけ新形式へ変換する。元のメニュー履歴を最初の明細へ引き継ぎ、欠落は欠落のまま残す。
- 保存キーは変更しない。versionless・v1・v2・v3を読み込む。読込みだけでは保存しない。新形式を保存する明示操作時にルートversionを3とし、v3はその後も3を維持する。新形式を含まない旧形式の通常保存は従来のv2で保存する。
- v3を旧版へ戻して編集・再保存することは保証しない。v2対応版のfuture version保存拒否を維持し、新版も未対応versionを上書きしない。
- ファイル・貼付文字列の両復元経路で明細配列・必須識別子・文字列・有限数値・非負値・明細内ID重複・合計を保存前に検査する。旧履歴から変換した明細の履歴値欠落を許容する。未知フィールドは削除しない。

### 3.7 明細分析基盤

**状態: `CONFIRMED`（2026-10-01）**

- 来店人数はentries件数、技術売上は来店price合計、客単価は技術売上÷来店人数。店販・総売上・時間の既存定義は維持する。
- 明細のmenuId、menuName、standardPriceAtVisit、categoryAtVisitごとに施術件数・実売上を集計する。メニュー施術件数を来店人数とは区別する。
- カテゴリー施術構成比はカテゴリー明細件数÷全明細件数。カテゴリー利用率は該当カテゴリーを含む来店数÷全来店数。同一来店の同一カテゴリーは利用来店数として重複計上しない。複数カテゴリーの利用率合計は100%を超え得る。
- カテゴリー→来店時標準価格→メニューまで内訳を取得可能とする。履歴欠落は不明グループとして保持し、現在値で再解釈しない。
- 今回は保存・入力・明細集計関数まで。価格改定履歴、有効日、比較期間、比較画面の詳細は別途決定する。

- 見落とし
- 反対意見
- 別解

- データ不足
- 重大なリスク

- 一致点
- 相違点
- 前提条件の違い
- 使用データの違い
- 不確実性
- 追加確認が必要な情報
- 判断が変わる条件
